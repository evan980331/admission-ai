## 5. 格式差異與解析難點

1. **字元碎裂**：列印 PDF 把詞拆成單字（`申請｜入｜學`、`大｜學申請`），
   且表頭跨 4 列，逐行正則不可靠，需 y 座標分群＋欄位重組。
2. **數字黏合**：樣本見 `1500115.05.16`（費用＋日期無分隔），需錨點切分。
3. **`無` vs 數字**：外加名額欄 `無`→null、`--`→null，沿 P3 `toNull` 即可。
4. 三校結構一致（同為甄選會查詢頁列印），**暂無校際格式差異**；
   但樣本僅 3 校＋總覽 1 檔，不能推論 64 校皆同，parser 必須逐檔驗證＋unknown 欄進 warning。

## 6. 是否需要 OCR

**不需要**。四檔皆文字型、零 U+FFFD、零空白頁。

## 7. 建議 parser architecture

```text
PDF（人工下載，raw 保留）
  → PDF intermediate extractor（新腳本，輸出 per-school JSON）
  → 現有 application115 CSV/JSON parser（不改）
  → normalize → validate → import → data_import_runs
```

- 不做 PDF→DB 直寫；中繼 JSON 欄位沿用 `CSV_COLUMNS`，缺值 null。
- extractor 為暫存→正式化兩階段：先以 001 三校驗證錨點解析率，達標才並入 pipeline。
- 不同學校先當不同格式測試，禁止寫死欄位順序。

## 8. 預估可自動化程度

| 目標 | 預估 |
|---|---|
| identity（校碼／系碼／系名） | ~90%（括號碼錨點穩定） |

| 檢定／倍率／二階 | 0%（來源檔無此資料，需明細頁） |

## 9. 目前無法可靠解析的欄位

換行切斷的系名黏合、費用＋日期黏合格、外加名額欄位對齊、
以及（最關鍵）所有篩選與二階欄位——因來源缺失而非技術問題。
